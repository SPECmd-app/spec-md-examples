# SPEC.md Examples

A growing collection of real SPEC.md files written for actual small projects, showing the format applied in practice.

This collection is what the SPEC.md site presents as its [Portables page](https://specmd-app.github.io/SPEC.md/portables.html). The page lists the Judo Club Website first, as the canonical example and a fully implementable portable, followed by the examples below.

This is separate from the versioned walkthrough example (the Judo Club Website, specified at each stage of the standard's own evolution), which stays in [`SPECmd-app/SPEC.md`](https://github.com/SPECmd-app/SPEC.md/tree/main/examples) alongside the standard itself. The examples here are independent, real specifications for their own projects — not tied to the standard's release cycle.

## Examples

- [`spec-md-website/SPEC.md`](spec-md-website/SPEC.md) — the SPEC.md for the SPEC.md project's own companion website (a static GitHub Pages site): what its homepage must link to, its machine-readable discovery files, its "no outside dependency" requirement, its consent-gated analytics, and its Portables page. Includes a [`TRACE.md`](spec-md-website/TRACE.md).
- [`specmd-cli/`](specmd-cli/) ([`README.md`](specmd-cli/README.md), [`SPEC.md`](specmd-cli/SPEC.md), [`TRACE.md`](specmd-cli/TRACE.md)) — the SPEC.md and paired TRACE.md for [`SPECmd-app/specmd-cli`](https://github.com/SPECmd-app/specmd-cli), a Core+Optional example with `optional_features.trace: true`. This is a snapshot copy; the four Normative Modules it declares live only in the `specmd-cli` repository, so links to them won't resolve here — see that repository for the complete, resolvable Specification Set.
- [`internal-it-ticketing-system/`](internal-it-ticketing-system/) ([`README.md`](internal-it-ticketing-system/README.md), [`SPEC.md`](internal-it-ticketing-system/SPEC.md)) — a Core-only example showing the Living Specification principle in practice: an internal IT service desk with only four decisions made so far (service-desk type, SSO scope for Agents, single-organization tenancy, intake channels), everything else explicitly left as `TBD` / Open Issues rather than invented.
- [`headless-bpm/`](headless-bpm/) ([`README.md`](headless-bpm/README.md), [`SPEC.md`](headless-bpm/SPEC.md), [`TRACE.md`](headless-bpm/TRACE.md), [`ERD.md`](headless-bpm/ERD.md), a [BPMN 2.0 XML example](headless-bpm/examples/starter-kit-request.bpmn) and its [changelog](headless-bpm/CHANGELOG_0.14.0.md)) — a large Core+Optional example (specification 0.14.0): a durable, BPMN 2.0-aligned business-process orchestration system with no built-in GUI, operated through CLI, REST and MCP. It uses `requirement_metadata`, Mermaid diagrams, composed verification and a paired TRACE.md, with a derived logical ERD companion. Implementation evidence in the trace is intentionally still `TBD` / planned.
- [`karesansui-japanese-garden-game/`](karesansui-japanese-garden-game/) ([`README.md`](karesansui-japanese-garden-game/README.md), [`SPEC.md`](karesansui-japanese-garden-game/SPEC.md), [`TRACE.md`](karesansui-japanese-garden-game/TRACE.md)) — a Core example with a paired TRACE.md (specification 1.16.0) for 枯山水 Karesansui, a single-file browser zen garden game that runs in a sandboxed iframe. It specifies the experience as well as the rules: exact simulation tables and a Tranquility formula, a `.garden` file format, a web-versus-phone layout intent, and normative wording (Table M), timing (Table Z), and small-screen rules, so that another agent building from it produces the same game. One open issue is left `TBD`.
